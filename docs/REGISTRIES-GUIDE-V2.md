# 🗂️ Реестры проекта: руководство для редакторов и разработчиков

> Для кого эта документация:для контент-менеджеров (гуманитариев) и разработчиков, помогающих вести мемориальный проект. Экспертиза не требуется — сложные вещи объясняем простым языком.
> Последняя сверка с кодом:`src/data/authors.yaml`,`src/content.config.ts`(Astro 6.x), ветка`main-qwen3`.

## 1. Введение: Философия реестров

### 1.1. Единый источник правды (Single Source of Truth)

Представьте: один и тот же автор — скажем, поисковый отряд «Ак-Монай» — упомянут в 30 статьях. Если данные об отряде хранятся внутри каждой статьи (во*frontmatter*), то при опечатке в названии или смене ссылки вам придется править 30 файлов. Забыли один — и на одном сайте висит устаревшая ссылка.

Мы поступаем иначе.Все «справочные» сущности — авторы, источники, войсковые соединения, кладбища — живут водном YAML-файле-реестре. Статья же только*ссылается*на запись реестра по её короткому`id`. Исправили запись в одном месте — обновился весь сайт.

```
┌─────────────────────────┐          ┌──────────────────────────┐
│  src/data/authors.yaml  │ ◄────────│  статья: authorIds: [...]│
│  (ЕДИНСТВЕННЫЕ данные   │  ссылка  │  (только список ID,      │
│   об авторах/источниках) │  по id   │   НИКАКИХ данных внутри) │
└─────────────────────────┘          └──────────────────────────┘
```

### 1.2. Три главных реестра проекта

**Где готовятся данные.** Карточки павших и файлы войсковых соединений готовятся в отдельном репозитории **https://github.com/annachurasheva/fallen-cards** — это внешний рабочий источник для `units.yaml`. Соединения приходят оттуда (словарь `warunits-fallen-cards.json/.md`, копия в `docs/Libraries/`) и будут оттуда же пополняться и уточняться; в наш реестр они переносятся по согласованию едиными коммитами. Объекты захоронений для реестра кладбищ отбираются по рабочей локации проекта — **Ленинский район, Республика Крым** (файл `docs/Libraries/memorial_objects_leninskyi_r.csv`, 14 учётных объектов OBD Memorial), а не по всей базе из 85 позиций.


| Реестр                | Файл                     | Что хранит                                                                                | Статус                         |
| --------------------- | ------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------ |
| Авторы и источники    | src/data/authors.yaml    | Персоны, библиотеки, сообщества, организации, редакции, архивные источники                | ✅ работает                     |
| Войсковые соединения  | src/data/units.yaml      | Части, дивизии, полки, отряды, в которых служили павшие                                   | ✅ зарегистрирован, наполняется |
| Мемориальные кладбища | src/data/cemeteries.yaml | Локации захоронений, паспорта объектов культурного наследия, координаты, охранные статусы | ✅ зарегистрирован, наполняется |

Все три реестра пересекаются: карточка персоны сможет ссылаться на`id`из`units.yaml`(где служил) и`cemeteries.yaml`(где захоронен). Об этом — в разделе 5.

### 1.3. ⚠️ Главный принцип: неинвазивность (Non-destructive approach)

Проект построен на базекоммерческого шаблона. Мы не имеем права разрушать или глубоко переписывать его оригинальную архитектуру — иначе мы потеряем возможность получать обновления шаблона, а любая правка станет минным полем для будущих мержей.

Наши расширения — это «аддоны» (надстройки), которые работают параллельно с оригинальным кодом:

| Что делаем                  | Как именно (изолированно)                                                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Добавляем реестр            | Новый файл src/data/*.yaml + отдельная коллекция в content.config.ts, оригинальные коллекции posts/about не трогаем                            |
| Связываем статью с реестром | Одно необязательное поле authorIds добавлено в схему posts; без него всё работает как раньше («мягкое» разрешение: пустой массив = нет автора) |
| Отображаем данные           | Наши компоненты (PostAuthor.astro) и утилиты JSON-LD рендерятся условно — только если ссылки есть; шаблонный рендер постов не ломается         |
| Пишем документацию          | Отдельная папка docs/ — ничего общего с кодом шаблона                                                                                          |

> Правило большого пальца:если изменение требует*переписать*логику шаблона — остановитесь и спросите, нельзя ли сделать*обёртку рядом*. Почти всегда можно.

## 2. Подробный гайд по`authors.yaml`

### 2.1. Структура файла

Файл — этоодин YAML-список(массив) объектов. Каждая запись начинается с дефиса`- `на нулевом отступе:

```yaml
- id: nevzorov-b-i              # ← новая запись начинается с "- "
  name: Невзоров Борис Ильич    # ← поля записи — с двумя пробелами
  type: персона
  credentials: кандидат исторических наук, доцент
  ...
```

Между записями принято ставить разделительный комментарий — это помогает глазу и поиску:

```yaml
# --- Персона: Борис Ильич Невзоров ---
```

### 2.2. Поле`type`и зависимость набора полей

Каждая запись обязана иметь`type`— строго одно из шести значений:

| type        | Кого записываем                   | Пример                                |
| ----------- | --------------------------------- | ------------------------------------- |
| персона     | Живой или исторический человек    | исследователь, волонтёр, автор очерка |
| библиотека  | Библиотека / читальня             | научная библиотека имени …            |
| сообщество  | Отряд, клуб, движение             | поисковый отряд «Ак-Монай»            |
| организация | Юрлицо, музей, архив              | общество краеведения                  |
| редакция    | СМИ, интернет-издание             | Bospor.com.ua                         |
| источник    | Книга, архивный фонд, база данных | памятная книга, ЦАМО                  |

Тип определяет, какие поляосмысленно заполнять(технически все поля кроме`id`,`name`,`type`необязательны, но логика такая):

| Группа полей                 | Поля                                                                                                                            | персона            | организации (библиотека, сообщество, организация, редакция, источник) |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------ | --------------------------------------------------------------------- |
| Внутренние (для сайта)       | credentials, access, license_note, link, note                                                                                   | ✅                  | ✅                                                                     |
| Schema.org — общие           | url, sameAs, image                                                                                                              | ✅                  | ✅                                                                     |
| Schema.org — для персон      | jobTitle, affiliation                                                                                                           | ✅                  | ❌ оставить пустыми                                                    |
| Schema.org — для организаций | schema_type, legal_name, alternate_name, founding_date, dissolution_date, successor, predecessor, parent_organization, location | ❌ оставить пустыми | ✅                                                                     |

> `schema_type`— техническое имя схемы Schema.org (`Person`/`Organization`). Он должен согласовываться с`type`:`персона`→`Person`, все остальные → обычно`Organization`.

### 2.3. Строгая уникальность`id`

`id`— это адрес записи.На него ссылаются статьи (`authorIds`), на нем строится JSON-LD, по нему люди ищут запись в файле. Поэтому:

1. `id`не повторяется внутри файла.Две записи с одинаковым`id`= ошибка сборки (`Duplicate entry id`) — Astro не соберёт контент.
2. `id`не повторяется между всеми файлами реестров.Когда появятся`units.yaml`и`cemeteries.yaml`, идентификаторы должны быть уникальны и*между*ними тоже. Если редакция совпадает с одноимённым сообществом — придумайте разные ключи:`redaktsiya-lenino`vs`soobshchestvo-lenino`.
3. Формат`id`:строчные латинские буквы, цифры и дефисы (транслит):`ak-monay`,`nevzorov-b-i`,`redaktsiya`. Без пробелов, точек, кавычек и кириллицы.
4. `id`неизменяем после публикации.Переименовали — порвали все ссылки. Если запись ошибочна — лучше создать новую с новым`id`, а старую пометить в`note`.

Поле`name`при этом может быть каким угодно (полное ФИО, название с кавычками) — оно для людей,`id`— для машины.

## 3. Технический нюанс: даты и «умный» парсинг YAML

### 3.1. Феномен smart parsing

YAML — язык слишком заботливый. Если написать датубез кавычек:

```yaml
founding_date: 1862-07-01
```

парсер YAML решит: «это же дата!» — и превратит её вобъект JavaScript`Date`, а не в строку. Наша Zod-схема ожидает строку и на объект заругается:

```
Expected type "string", received "object"
```

(Да, объект. Для компьютера`Date`— объект, хотя человеку видно «просто дату».)

### 3.2. Наше решение:`z.preprocess`

Чтобы не заставлять редакторов помнить про тонкости парсеров, в`src/content.config.ts`для полей дат стоит автоматический «переводчик»:

```ts
// ИСПРАВЛЕНИЕ ДАТ (автоматический перевод Date-объектов в строки):
founding_date: z.preprocess((val) => {
  if (val instanceof Date)
    return val.toISOString().split('T')[0]   // Date → 'YYYY-MM-DD'
  return val                                  // строку пропускаем как есть
}, z.string().optional()),
```

То есть: что бы YAML ни сконвертировал в`Date`, Zodсам вернётего к каноничной строке`YYYY-MM-DD`. Данные не портятся, сборка не падает.

### 3.3. ✅ Правило: даты пишем строго БЕЗ кавычек

```yaml
founding_date: 1862-07-01     # ✅ правильно (plain style)
founding_date: '1862-07-01'   # ❌ плохо: ESLint (yaml/plain-scalar) требует убрать кавычки
```

Почему так: наш линтер ESLint с плагином для YAML правилом`yaml/plain-scalar`подсказывает, что скаляр, который YAML*может*прочитать сам (число, дата,`true`), не нужно оборачивать в кавычки без необходимости. Даты без кавычек +`preprocess`в схеме = чистый линтеричистая сборка. Два механизма страховки работают вместе.

Формат даты — только ISO:`ГГГГ-ММ-ДД`. Если известен только год — пишите строкой`1862`(Zod примет любую непустую строку; partial-дату вида`1862-07`тоже можно, но полный ISO предпочтительнее).

## 4. Правила заполнения пустых значений

Запись заполняетвсе поля из канона— даже те, что не нужны. Пустое — не значит «отсутствует», пустое значит «проверено, информации нет». Это делает записи однотипными и удобными для поиска.

| Тип значения               | Как пишем                                     | Пример           |
| -------------------------- | --------------------------------------------- | ---------------- |
| Пустая строка              | два апострофа ''                              | license_note: '' |
| Пустой массив              | квадратные скобки []                          | sameAs: []       |
| Неизвестно/нет данных      | 'нет данных' в note или ''                    | access: ''       |
| Целая строка поля не нужна | можно пропустить строку (поле optional в Zod) | —                |

Категорически запрещено:

```yaml
link: # ❌ «висячее» двоеточие без значения — YAML прочитает null,
#    а схема ждёт string → ошибка валидации
note: null # ❌ null тоже не string
```

> Лайфхак:скопируйте последнюю запись того же`type`, вставьте ниже, замените значения. Канон не сломается, опечаток в именах полей не будет.

## 5. Реестры`units.yaml`и`cemeteries.yaml`— зарегистрированы и работают

*(раздел для разработчиков и продвинутых редакторов)*

**Внешний рабочий источник для `units.yaml`:** подготовка карточек павших и файлов войсковых соединений ведётся в отдельном репозитории **https://github.com/annachurasheva/fallen-cards**. Соединения берутся оттуда (словарь `warunits-fallen-cards.json/.md`, зеркало — в `docs/Libraries/`) и пополняться/уточняться будут тоже там; в `src/data/units.yaml` изменения переносятся по согласованию едиными коммитами. Приоритет при расхождении данных: актуальная версия в `fallen-cards`.

Архитектура скопирована с паттерна`authors.yaml`один в один, как и планировалось:

1. YAML-файлы в`src/data/`— тот же формат «массив записей с`id`».
2. В`content.config.ts`—отдельные`defineCollection`(`unitSchema`,`cemeterySchema`) с изолированными loader'ами (`glob({ pattern: 'units.yaml', base: './src/data' })`). Оригинальные коллекции шаблона (`posts`/`about`) не тронуты — принцип неинвазивности соблюдён.
3. Уникальность`id`— глобальная, через все три реестра (см. п. 2.3).
4. Даты — общий helper`isoDate()`(`z.preprocess`: Date → строка`YYYY-MM-DD`).
5. Документальные позиции не меняем.Поля, где источник даёт «строку, похожую на число» (`passport_number`с слэшем`82-289/2023`,`obd_document_id`,`buried_known/unknown`), защищены`z.preprocess`от number→string; значения из CSV переносятся символ в символ.
6. Внешние ссылки на сервисы МО РФ(obd-memorial.ru, memmo.ru): официальное предупреждение Минобороны требует российских сертификатов / корневого сертификата Минцифры. Поэтому: ссылка хранится как есть + метка`[Минцифры]`в`note`; автоматическая проверка доступности при сборке НЕ делается; карточка самодостаточна (данные CSV дублируются в полях).

### 5.3. Как контент-менеджер связывает сущности

> ⚠️ Ссылки «мягкие» (soft resolve): несуществующий ID не должен ронять сборку — компонент
> просто проигнорирует его и выведет предупреждение. Так защищает нас от опечаток редактора.

**География наполнения.** Проект ведёт локацию **Ленинский район, Республика Крым**.
В исходном CSV `docs/Libraries/memorial_objects_leninskyi_r.csv` этой территории соответствуют
**14 объектов захоронений** , а не все не все мемориалы из `docs/Libraries`.
Остальные позиции CSV понадобятся при указании перезахоронений  по мере заполнения карточек павших
и в `cemeteries.yaml` заносятся только по факту. Ручной контроль id выполняется только по этим 14 позициям.


Точно так же, как сейчас связывает статью с авторами —массивами ID:

```yaml
---
title: Очерк о бойце 276-й дивизии
published: 2026-03-01
authorIds: [ak-monay, nevzorov-b-i] # работает сегодня
unitIds: [unit-276-00] # коллекция зарегистрирована
cemeteryIds: [simferopolskiy-trudovoe] # коллекция зарегистрирована
---
```

Плюс внутри самих реестров перекрёстные ссылки уже предусмотрены: запись кладбища содержит поля`units`(кто здесь захоронен) и`sources_authors`(ид источников).ID во всех массивах — строки в кавычках(массив ID не является датой/числом, кавычки здесь обязательны и линтеру не мешают).

> ⚠️ Ссылки «мягкие» (soft resolve): несуществующий ID не должен ронять сборку — компонент просто проигнорирует его и выведет предупреждение. Так защищает нас от опечаток редактора.
